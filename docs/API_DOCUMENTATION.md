# CampusLoop — API Documentation

Base URL (development): `http://127.0.0.1:8000/api/v1`
Interactive reference: `/docs` (Swagger UI) · `/redoc` · `/openapi.json`

All routes are versioned under `/api/v1`. The OpenAPI document is generated by FastAPI from the Pydantic schemas and is the source of truth for request/response fields.

---

## 1. Conventions

### Authentication

- `POST /auth/login` returns `access_token`, `refresh_token`, `token_type`, `expires_in` and the user object.
- Send `Authorization: Bearer <access_token>` on protected requests.
- Access tokens expire after 30 minutes; refresh tokens after 7 days.
- `POST /auth/refresh` with `{ "refresh_token": "…" }` returns a new pair.
- The client retries one 401 after refreshing; a failed refresh clears the session.

### Roles and gates

| Dependency | Meaning |
| --- | --- |
| Public | No token needed; optional token improves personalisation (`is_wishlisted`) |
| Authenticated | Valid access token |
| Verified | Authenticated **and** `verification_status = verified` (admins pass) |
| Admin | Authenticated **and** `role = admin` |

### Errors

```json
{
  "detail": "Please check the highlighted fields.",
  "code": "validation_error",
  "errors": [{ "field": "email", "message": "value is not a valid email address" }]
}
```

| Status | Meaning |
| --- | --- |
| 200 / 201 | Success / created |
| 400 | Business rule failure (`bad_request`) |
| 401 | Missing/invalid token (`unauthorized`) |
| 403 | Authenticated but not allowed (`forbidden`) |
| 404 | Not found or hidden by visibility rules (`not_found`) |
| 409 | State conflict, duplicate, already sold (`conflict`) |
| 422 | Schema validation (`validation_error`, field list) |
| 429 | Rate limit exceeded |
| 500 | Sanitised server error (`server_error`) |

Stack traces and database details are never returned.

### Pagination

Paginated endpoints return:

```json
{ "items": [], "total": 42, "page": 1, "page_size": 12, "pages": 4 }
```

Use `page` (≥ 1) and `page_size` (1–60; 100 in admin lists).

### Dates and money

- API timestamps are UTC ISO-8601. The frontend appends `Z` when the API omits an offset so local display is correct.
- Money is returned as a JSON number with two-decimal database precision. The UI formats it as INR (`₹1,25,000`).

## 3. WebSocket protocol

**Endpoint:** `ws://127.0.0.1:8000/api/v1/ws/chat/{conversation_id}?token=<access_token>`

The token is verified before the socket is accepted. Membership is checked against the conversation. Close codes:

| Code | Reason |
| --- | --- |
| 4401 | Missing/invalid token |
| 4403 | Authenticated but not a participant |
| 4404 | Conversation not found |

### Client → server

```json
{ "type": "ping" }
{ "type": "typing" }
```

Messages are sent through `POST /conversations/{id}/messages` (persistence first); the server broadcasts the saved message to the room.

### Server → client

```json
{ "type": "ready", "conversation_id": "…" }
{ "type": "message", "message": { "id": "…", "sender_id": "…", "body": "…", "message_type": "text", "created_at": "…" } }
{ "type": "typing", "user_id": "…" }
{ "type": "read", "user_id": "…" }
{ "type": "offer", "offer_id": "…" }
{ "type": "meeting", "meeting_id": "…" }
{ "type": "transaction", "transaction_id": "…" }
{ "type": "pong" }
```

On `offer`/`meeting`/`transaction` events the client refetches conversation detail, so authoritative state always comes from the database.

## 4. End-to-end examples

### Register and verify

```bash
curl -X POST http://127.0.0.1:8000/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{
    "full_name": "Ananya Sharma",
    "email": "ananya@college.edu",
    "college": "IIT Delhi",
    "student_id_number": "2021CS1042",
    "department": "Computer Science",
    "course": "B.Tech",
    "year": 3,
    "password": "Student123",
    "confirm_password": "Student123"
  }'
```

Submit verification, then approve it as an admin:

```bash
# student
curl -X POST http://127.0.0.1:8000/api/v1/verifications/me \
  -H "Authorization: Bearer $STUDENT_TOKEN" \
  -F "college=IIT Delhi" -F "student_id_number=2021CS1042"

# admin
curl -X POST http://127.0.0.1:8000/api/v1/admin/verifications/$VERIFICATION_ID/decision \
  -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"status":"verified"}'
```

### List an item

```bash
curl -X POST http://127.0.0.1:8000/api/v1/products \
  -H "Authorization: Bearer $STUDENT_TOKEN" -H "Content-Type: application/json" \
  -d '{
    "title": "Dell Inspiron 15 · 8GB RAM",
    "description": "Bought in 2022, battery lasts 4 hours, charger included.",
    "category_id": "<category-uuid>",
    "price": 28000,
    "original_price": 52000,
    "condition": "good",
    "brand": "Dell",
    "location": "IIT Delhi",
    "location_details": "Hauz Khas, New Delhi, Delhi, 110016, India",
    "latitude": 28.545, "longitude": 77.1926,
    "age_months": 30,
    "image_urls": ["/uploads/public/products/abc.jpg"]
  }'
```

`location_details`, `latitude` and `longitude` are optional. Latitude and longitude must be supplied together; the frontend search, geolocation and map pin produce all three. Coordinates are returned on the product detail endpoint and drive the pickup map.

The listing returns as `pending_verification` until an admin approves it.

### Negotiate and complete

```bash
# buyer starts a chat
curl -X POST http://127.0.0.1:8000/api/v1/conversations \
  -H "Authorization: Bearer $BUYER_TOKEN" -H "Content-Type: application/json" \
  -d '{"product_id":"<id>","message":"Is this still available?"}'

# buyer offers
curl -X POST http://127.0.0.1:8000/api/v1/offers \
  -H "Authorization: Bearer $BUYER_TOKEN" -H "Content-Type: application/json" \
  -d '{"conversation_id":"<id>","amount":25000}'

# seller accepts
curl -X PATCH http://127.0.0.1:8000/api/v1/offers/<offer-id> \
  -H "Authorization: Bearer $SELLER_TOKEN" -H "Content-Type: application/json" \
  -d '{"action":"accept"}'

# buyer starts the transaction at the agreed price
curl -X POST http://127.0.0.1:8000/api/v1/transactions \
  -H "Authorization: Bearer $BUYER_TOKEN" -H "Content-Type: application/json" \
  -d '{"offer_id":"<offer-id>"}'

# both confirm
curl -X POST http://127.0.0.1:8000/api/v1/transactions/<tx-id>/confirm -H "Authorization: Bearer $BUYER_TOKEN"
curl -X POST http://127.0.0.1:8000/api/v1/transactions/<tx-id>/confirm -H "Authorization: Bearer $SELLER_TOKEN"
```

After the second confirmation the transaction is `completed` and the product becomes `sold`. The buyer can then `POST /reviews`.

### Paginated marketplace query

```bash
curl "http://127.0.0.1:8000/api/v1/products?q=laptop&condition=good&condition=like_new&min_price=10000&max_price=40000&sort=price_asc&page=1&page_size=12"
```

## 5. Rate limits

| Endpoint group | Limit |
| --- | --- |
| Login | 10 / 5 min per email+IP |
| Register | 5 / hour per IP |
| Forgot password | 5 / hour per email+IP |
| Reports | 10 / hour per user |
| Uploads | 40 / hour per user |
| Messages | 120 / minute per user |

Implemented in-memory (`app/core/rate_limit.py`), disabled in tests. For multi-instance deployments, replace with a shared store.
